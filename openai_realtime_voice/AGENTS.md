# Server Addon — Agent Guide

## Design intent

This addon is a **direct WebSocket bridge** between the Voice PE device and the OpenAI Realtime API. It receives raw PCM over WebSocket, forwards it to Realtime, and streams response audio back. Implementation is a single Python module (`app/main.py`) plus optional recording.

**Lifecycle:** One client connection = one OpenAI Realtime session. The
three forwarding tasks (client→OpenAI, OpenAI→client, output_sender) run
concurrently; the first to finish (client disconnect, OpenAI disconnect,
or `disconnect_client` tool) triggers cancellation of the other two and
immediate closure of both WebSockets. No polling a done flag — cleanup
is prompt and predictable. Session end is logged with duration and reason.

## Architecture

```
ESP32 Voice PE                    Addon
+------------------+  WebSocket   +---------------------------+
| micro_wake_word  |   :8080     |  RealtimeVoiceBridge      |
| voice_assistant  | --- PCM ---> |    client_ws <-> openai_ws|
| _websocket       | <--- PCM --- |    (one openai_ws per     |
| I2S Speaker      | <-- JSON --  |     client connection)    |
+------------------+             +---------------------------+
                                       | disconnect_client tool
                                       | search_web tool ------> Responses API
```

- **Audio:** 24 kHz, 16-bit, mono PCM. Device binary frames are base64-encoded and sent as `input_audio_buffer.append`; `response.output_audio.delta` (Realtime API GA) is base64-decoded and sent as binary to the device.
- **Interrupt:** Device sends `{"type":"interrupt"}`; server sends `response.cancel` to OpenAI.
- **Stopped:** when the device ends a conversation it sends `{"type":"stopped","reason":"auto_stop","ms":242262}` just before closing; the server logs `Device ended the conversation: <reason> after <ms> ms` (reasons are listed in `state_machine.h`, `Stop`). If the socket is already gone the reason is only in the device log.
- **Disconnect:** When the user says goodbye, OpenAI calls `disconnect_client`; server sends `{"type":"disconnect"}` to the device, returns from the handler so the task ends, and the cancellation cascade closes both WebSockets.
- **Web search:** The `search_web` tool calls the OpenAI Responses API (GA `web_search` tool, `gpt-4.1-mini` model) using `WEB_SEARCH_API_KEY` or `OPENAI_API_KEY`. Non-reasoning search is used for low latency (single lookup, typically 3–10s). The key must have **Responses (Write)** permission in the OpenAI dashboard.

## Design decisions

- **No MCP.** Smart home is intended as a separate, local HA voice pipeline (e.g. different wake word). This addon is for voice Q&A and web search only.
- **Realtime API GA.** The addon uses the GA interface (no beta header); session config uses GA shape (`audio.input`/`audio.output`, `type: "realtime"`); server events are `response.output_audio.delta` / `response.output_audio.done`.
- **Two tools:** `disconnect_client` and `search_web`, both in `main.py`. `disconnect_client` is handled synchronously in `_handle_tool_call` (ends session). Other tools (e.g. `search_web`) run in the background via `_run_tool_in_background` so the event loop stays responsive and the model can acknowledge the user while a tool is pending.
- **Async function calling (GA):** The Realtime API supports the model continuing the conversation while a tool is pending (user can ask "how much longer?" and the model responds). The model does NOT reliably speak before calling tools regardless of instructions; instruction-based pre-acknowledgment was tested and failed. See [developer blog](https://developers.openai.com/blog/realtime-api).
- **Phase protocol:** The server sends `thinking`, `replying`, and `searching` phases only. "listening" was removed — the client derives it locally from audio playback state (`is_bot_speaking()` transitioning false). This eliminates the race where "listening" was sent at `response.done` before knowing if another response (with a tool call) would follow, which caused a brief green flash between replying and searching. At `response.done`, if `pending_tool_tasks` is non-empty, the server sends `searching`; otherwise no phase is sent. **All phases** go through a single **output queue** and are sent to the client in order by `_output_sender`; this eliminates race conditions and keeps LED/UX in sync with what the user hears. The client uses phase to show a distinct state (blue-green LEDs) and a 60s auto-stop timeout so long searches don't kill the session.
- **Tool call deduplication:** In-flight `search_web` calls are deduplicated by query. If the model issues the same query again while a search is already running (e.g. user asks "what's taking so long?" and the model redundantly calls search again), the server reuses the first result for the duplicate call and does not trigger a second `response.create`, avoiding duplicate spoken answers.
- **Stale tool results:** When the user moves on before a search completes, the old result may still be sent and the model may read it back. Deduplication only covers same-query duplicates while a search is in flight; cancelling on speech would break the "how much longer?" use case.
- **Web search:** Responses API with `gpt-4.1-mini` (non-reasoning) typically completes in 3–10s; httpx timeout is 45s. `response_idle` prevents sending tool results while the model is mid-speech.
- **Config:** HA Addon UI → `config.yaml` → `run.sh` (bashio) → env vars → `main.py`. No config file parsing in Python.

## Config options

- `openai_api_key` — Required. Must have **Realtime (Request)** permission. Also used for web search if `web_search_api_key` is unset, in which case it must also have **Responses (Write)**.
- `websocket_port` — Default 8080.
- `vad_threshold`, `vad_prefix_padding_ms`, `vad_silence_duration_ms` — Server-side VAD.
- `instructions` — Optional extra rules, appended after Leyla's instructions. Leyla's instructions themselves live in `app/persona.py`.
- `voice` — OpenAI Realtime voice (default `marin`).
- `realtime_model` — OpenAI Realtime model (default `gpt-realtime`). Constructs the WebSocket URL as `wss://api.openai.com/v1/realtime?model={realtime_model}`. For full URL override, set `OPENAI_REALTIME_URL` env var directly.
- `web_search_model` — Model for Responses API web search (default `gpt-4.1-mini`).
- `web_search_api_key` — Optional; if empty (or whitespace-only), `openai_api_key` is used for web search. Must have **Responses (Write)** permission. A 401 on web search means the key lacks this permission.
- `lamp_show`, `lamp_show_lights` — Lamp show (see `app/lamp_show.py`): on by default, comma separated light entities.
- `enable_recording` — If true, WAVs written under `recordings/` via `app/audio_recorder.py`.

## Adding a tool

1. Put the tool schema (`..._TOOL` dict with `name`) and its `run(args)` coroutine in its own module and add the schema to the tools list of `_session_start`.
2. Register it in `ToolLinkMixin._build_tools` (`app/tool_link.py`): label, timeout, `run`, the friendly error text, and optionally `gate(args, state)` (return an error result to refuse, for example for anyone but Metin), `after`, `log`, `phase`. The generic `_run_tool` runs it in the background with a timeout and returns the result, so there is no per tool runner code. `end_conversation` is the only function handled inline in `_handle_backend_event`.
3. Add a case to `tests/test_session_flow.py` when the tool has a gate or special behavior.

## Docker build

Single-stage Alpine image. Dependencies in `requirements.txt` (websockets, httpx, python-dotenv). Dockerfile runs `pip install -r requirements.txt`; no Poetry or LLVM.

## Version

When you change the addon (behavior, config, contract, or fixes), update the addon version in `config.yaml` using semver-like rules: breaking → bump major, new feature → minor, fix → patch. Do this until we have a better release/versioning solution.

## Session learnings (GPT Live)

- The memory page script lives in a normal Python string: write `\\n` and `\\s` in the source for `\n` and `\s` in the JS, and run `node --check` on the extracted `<script>` before every commit (a bare `\n` broke the page once on 15 Nov 2026; it was caught before installing).

- A false wake is ended with `no_speech` (`_no_speech_over`): the wait of 6 s counts from the end of Leyla's own greeting, not from the start (before, the greeting used up about half of the 8 s and she hung up while the user was answering), a voice heard in the last 2.5 s (microphone chunk rms 300 or more) holds the session open, and a hard limit of 14 s after the start applies so TV noise cannot keep a false wake alive. The transcript, which sets `user_spoke`, arrives a little after the words.

- The httpx logger is set to WARNING: it wrote one INFO line per Home Assistant request (to-do sync every minute, four lists) and pushed the useful lines out of the Supervisor log, which only keeps about the last 100 lines. The to-do sync interval is back at 30 s (the requests are cheap, only the log noise was the problem).

- GPT Live streams reply audio at about real time. `_output_sender` holds each reply until 200 ms are buffered and then stays 200 ms ahead of playback; without that reserve the first words stuttered. The Voice PE queues only 10 chunks of 20 ms while its speaker starts, so keep the lead at 200 ms or the ESP drops audio.
- Voice message in the app (2.151.0, setting `hoeren` in `/data/leyla_recall.json`, switched with `POST /api/kopf/settings`): 0 = the recording is transcribed, the chat model answers, GPT Live says the written answer (`chat.speak_prompt`). 1 = she also hears the recording herself: `voice_in.to_pcm` (ffmpeg), then one GPT Live session with `LISTEN_NOTE`, the recording in real time and, after it, `chat.hear_prompt` with the written answer as content (`announce_voice._collect_speech(heard=...)`). The order is measured, not chosen: a content note before the recording makes her talk into it, and audio fed faster than real time is an error.
- Fan frames (2.160.1): the fan does not act on every radio frame (one right after another, or one it takes for a repeat). All frames to the fan go through `FanController._send` (at least `FRAME_GAP_S` apart), `set_light` presses again while the power meter sees no change (`LIGHT_TRIES`), and `main._automation_command` runs the `leyla_command` events of one device in their order (a lock per device), because each event is its own task and a quick command used to overtake a slow one.
- Umziehen in the app menu (2.160.0): `menuItems` has `outfit`; `openSec('outfit')` sets `menuSub` and `drawMenu` then shows the folder (`WEAR`: arbeit, freizeit, nacht, plus the back row `mback`); a tap calls `wear(k)` → `POST /api/outfit` (code word) → `Heart.wear(outfit)` (any level, no scene, until 5 o'clock) and starts the loop of the new outfit with `stagePlay([], clipFor(st))`, because `stageMood` alone only swaps the still on an outfit change. The chat scenes `umziehen`, `bett` and `anziehen` keep their conditions.
- The end of a lamp show (2.159.2): a Matter lamp can show a look while its own on/off state, and with it Home Assistant, says off; a plain off then does nothing, on and then off does. It happens when commands overtake each other in the lamp: never cancel a `light.turn_on` that is on its way (Home Assistant sends it anyway; the worker ends through `_quit` after its call), never send an off into a fade that is still running, and put a lamp that was off back with on (white, `transition` 0), a wait, then a plain off (`_restore_one`), followed by a second off (`_off_again`). The state Home Assistant reports cannot prove that a lamp is dark; only Metin's eyes can, so ask him. Times in `hass.states` (`last_changed`) are UTC: read them with `toLocaleTimeString`, a wrong hour sent a whole diagnosis the wrong way on 24 Nov 2026.
- Leftovers of the lamp show (2.159.1): a lamp counts as restored only when it reports the wanted state and no look of the show (`LampShow._leftover`: today's looks or one of the looks really sent, `_shown`, kept in `/data/lamp_show.json`); a lamp that is on in such a look and not pending counts as off in `_snapshot`. Test changes to the show with lamps that are ON before it, and with the fake lamp reporting late (`test_lamps_that_were_on_come_back_even_when_they_report_late`); with lamps off before, everything always looked fine.
- Her mood on the rear lamps (2.159.0, replaces the 5 percent of 2.89.0): `LampShow.set_mood(low)` (from `_unlock_effects`, `_maybe_mood_lamp` and after the tool `laune`; `Mood.is_low` / `Heart.is_low`) switches the show to its second set of looks (colour keys `sad_listen`, `sad_think`, `sad_speak_low`, `sad_speak_high`; strengths `levels` with `listen`, `think`, `speak` and the same with `sad_`, percent 1 to 100, in `/data/lamp_colors.json` under `pct`). `set_colors(colors, levels)` takes both, `GET /api/lamp` returns `levels`, `POST /api/lamp/colors` takes `colors` and `levels`, `/api/lamp/test` takes `sad_listen` and so on. `is_show_look(state, colors, levels)` knows a leftover by hue and by the strength of that look, so a new look must be added to `show_looks`. To see the app section without a server, open the page with Playwright and call `openSec('lamps')`.
- A name is not the code word (2.158.4): anyone can say "ich bin Metin", and the name says nothing about who else is in the room. A Metin known only by his words gets `talk_notes.KNOWN_WITHOUT_CODE` (warm like to the family, no flirting, her small secret hidden: at most one ambiguous hint per talk), never her heart note (`mood.voice_note`), never the open chat question (`ideas.voice_note`), and a session start without an `unlock` item gets `START_HEAD_OPEN`, never "MIT METIN ALLEIN". Everything of the two of them (heart, `UNLOCKED_LOVE`, chat, private list) comes only with the code word. Before adding a note for a known speaker, ask: would it be fine if a visitor heard what she makes of it? Found on 24 Nov 2026 when she flirted openly after he only said his name.
- She guides like a teacher (2.162.0, Metin 24 Nov 2026): `persona.GUIDE` (section ZEIGEN, WAS DU KANNST) is appended in `persona.build` right after the core, only when `devices` is not empty (a talk at home or a live talk from the app); the chat gets its own line at the end of `chat.CHAT_ABILITIES_NOTE`. Its last rule keeps a clear request fast (no explaining, no questions). A section name may appear only once in her rules (`test_one_clear_package`), so never name another section inside a rule.
- Tool schemas (found 24 Nov 2026 while building the planner): in `tv.build_tool` the argument `volume_percent` had slipped outside of `properties` (listed as required, but no property), so an exact TV volume could not be asked for, and nothing complained. `tests/test_planer.py::test_tool_schemas_name_every_required_argument_as_a_property` now holds every plannable tool to: `required` equals the properties, nothing else next to them. Add a new tool to that test.
- The lamp show and anything that switches lamps 1 and 2 for good: at the end of a talk the show puts its lamps back to what they were BEFORE the talk. A switch during the talk (spoken, from the chat, or a plan) is undone for those lamps. The planner waits for `LampShow.busy` to end (2.161.0); spoken commands in a talk and the chat do not, that is still open.
- Fixed commands (`app/befehle.py`, 2.155.0): a sentence of the family that always switches the same lamps and fan parts. Two backend tools: `fester_befehl` (anyone) and `befehl_festlegen` (Metin: code word or known by his words). The list of commands goes into the backend hint at every session start (`Commands.hint()`); the model recognises the sentence, the code decides what is switched. Do not teach lamp rules as free sentences in the memory lists any more.
- What she is handed in a spoken talk lives in `app/talk_notes.py`. Rule, measured on 24 Nov 2026: **while GPT Live takes appended context it does not hear** (about 1500 characters a second, on `commentary`, `thinking` and `instructions` alike; speech in that time is lost, not delayed). So knowledge belongs into the session start: `instructions` (16 384 tokens) and startup `input` (8 192 tokens). A live talk from the app does that (`_app_start`, since 2.153.0). At home the code word comes in a running talk, so only `START_CHARS` (4500 characters, setting `start_chars`) are appended and the rest is held back; with the setting `frisch` (2.155.0, default off until measured at home) a new session with everything in its start takes the place of the running one (`_go_fresh`; every talk holds its connection as a `live_link.LiveLine`, so pass that object on and never keep the raw websocket of a talk). `session.commentary.append` is for what she shall say aloud; do not use it for memory. The exchange (`_go_fresh`, since 2.158.1) starts the new session at once and swaps it in when she has been silent for `FRESH_QUIET_S` and his last word in the transcript (`state["last_speech_at"]`) is `FRESH_HE_QUIET_S` old; never read "the room is quiet" from the microphone level at home (`last_voice_at`): with the TV on it never is, which made the first real exchange cut into her answer on 24 Nov 2026.
